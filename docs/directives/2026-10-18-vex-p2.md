## 1. GitHub App（用户只需在浏览器中点击）

- **创建命令**：`vex github create-app --owner imdomestic --name <名称> --out <目录>`，走 GitHub 的 App Manifest 流程：
  - 在本机临时监听 `127.0.0.1` 的一个随机端口作为回调地址；
  - 打开浏览器，显示预填好的 manifest；
  - 用户点「创建」后，CLI 用回调中的 code 换取 App 凭据，写入 `<目录>`：`app.json`（id、slug、client_id，均非秘密），以及 `private-key.pem`、`client-secret`（0600）。
- **manifest 内容**：
  - `public: false`
  - 权限：`actions: read`、`checks: write`、`contents: read`、`metadata: read`、`pull_requests: write`
  - 不配置 webhook，因为 encore 不对公网开放。
- **用户需要做的三件事**：
  1. 点「创建」；
  2. 在 App 设置中勾选 Enable Device Flow；
  3. 把 App 安装到 `imdomestic/chorus` 和 `imdomestic/vex-example-fabric`。

  其余步骤由智能体完成。
- **密钥部署**：私钥和 client secret 放进 nix-config 的 SOPS，部署到 `/var/lib/vex/secrets/`，权限为 root:vexd 0640。`vex-build` 不能读取它们。
- **检查命令**：`vexd github check`，列出 App 身份、各个安装、实际拿到的权限，以及每个项目对应仓库是否可以访问。

## 2. vex.toml

- 按设计 §7.1 解析 `schema = 1`，所有取值都要在 operator 设定的范围内校验：
  - `java` 必须存在于 runtimes 中；
  - `rooms.memory` 不能超过配额；
  - 依赖必须同时提供 sha1 和 sha512。
- 提交中没有 `vex.toml` 时，使用 `manifest_fallback`。把 P1 写在 `projects.<p>.minecraft` 和 `loaders` 里的内容迁移到 chorus 的 fallback 清单里。
- 在 `world.extra_root_entries` 生效后，删除 P1 中的项目配置项 `worlds.extra_root_entries`。

## 3. vex-action

- 新建公开仓库 `imdomestic/vex-action`。之所以必须公开：公开仓库的 workflow 不能使用私有仓库里的 action。LICENSE 由用户决定，在决定之前不添加。
- **实现**：一个独立的 Go 模块，即 bundler，在 action 运行时编译，构建缓存由 `actions/setup-go` 负责。
- **行为**：
  1. 读取 `vex.toml`；
  2. 在用户自己的构建步骤完成后，按各 loader 的 `files` 规则收集产物；
  3. 下载 `deps` 并校验哈希；
  4. 生成 `vex-build.json` 和 `files/` 目录；
  5. 用 `actions/upload-artifact` 上传，产物名默认为 `vex-build`。
- **`vex-build.json` 的格式**：
  ```json
  {"schema":1,"minecraft":"26.3","java":25,
   "loaders":{"fabric":{"loader_version":"0.19.5","files":[
     {"name":"x.jar","path":"files/fabric/x.jar","side":"both","size":0,
      "sha1":"…","sha256":"…","sha512":"…","origin":"build"},
     {"name":"fabric-api.jar","path":"files/fabric/fabric-api.jar","side":"both","size":0,
      "sha1":"…","sha256":"…","sha512":"…","origin":"dep","url":"https://…"}]}}}
  ```
  - 格式规范写在 vex 仓库的 `docs/bundle.md`。
  - 两个仓库各存一份相同的测试向量，用来保证 bundler 和 vexd 对格式的理解一致。
- **push 模式本轮不做**（设计 v0.4 已推迟到 P5）。

## 4. CI 产物拉取（pull 模式）

- **配置项**：`projects.<p>.github.repository`，以及 `projects.<p>.ci` 下的 `mode = "pull"`、`workflow`、`artifact`、`pr_previews`、`fork_previews`、`preview_access`、`poll_interval`（默认 60s）、`comment_language`（默认 `en`；我们的两个项目设为 `zh-CN`）。
- **轮询**：用 installation token 读取 `workflow` 下已完成且结论为 success 的 run，带 ETag 做条件请求。open PR 列表也单独带 ETag 轮询。
- **以 GitHub API 为准**：`head_sha`、事件类型、分支，以及该 run 对应哪个 PR，都以 GitHub API 返回的为准，不使用 bundle 里自报的值。
  - fork PR 的 run 中 `pull_requests` 字段为空，需要用 head sha 加 head 仓库去匹配 open PR。
- **下载与校验**：下载 artifact 后，在限额内安全解压，必须满足：
  - 拒绝绝对路径、`..`、符号链接、重复路径；
  - 设置总大小和文件数上限。

  随后由 vexd 重新计算每个文件的大小和三种哈希，与 `vex-build.json` 逐项比对，并解析 mod 元数据。任何一项不通过，整次构建都失败。
- **Build 记录**：
  - ID 仍为 `<loader>-<sha12>`，每接受一次 run 记为一个 attempt；
  - `source` 字段为 `{kind:"ci", runId, runAttempt, workflow, event, htmlUrl}`；
  - vex-agent 照常由平台作为服务端文件注入。
- **fork PR**：按 `fork_previews` 处理。
  - `off`：忽略。
  - `approval`：在当前 head sha 之后，有仓库写权限的成员评论 `/vex preview`，或者给 PR 加上 `vex-preview` 标签，才接受该产物。权限通过 App API 查询。其他人的评论一律忽略。
  - `auto`：直接接受。
- **构建来源**：chorus 和 example 都改为 `build.source = "ci"`。宿主机构建保留，但只供 trusted 项目使用，P5 再删除。

## 5. PR 房间

- **房间信息**：房间类型为 `pr`，ID 为 `pr<number>-<loader>`，附带字段 `pr: {number, title, author, url, headSha, fromFork}`。
- **创建**：第一个 Build 就绪后登记房间，状态为 stopped，由连接唤醒或 API 启动。
- **跟随新提交**：PR 有新 Build 时，房间在无人且无租约的情况下滚动到新 generation，世界沿用。这一项在 P2 只对 PR 房间生效；分支房间的 `on_new_head` 留到 P3。
- **关闭**：PR 关闭或合并后，依次进入 stopping、归档、closed。
- **白名单**：按 `preview_access` 决定：
  - `members`：项目成员；
  - `linked`：任何已绑定 MC 账号的 vex 用户；
  - `public`：关闭白名单，但保持 online-mode。
- **API**：新增 `GET …/pulls`，返回 open PR，以及每个 PR 的预览房间和 Build。

## 6. PR 评论与 check

- **评论**：每个 PR 只维护一条评论，以 `<!-- vex:preview project=<p> -->` 标记，之后原地更新。评论 ID 记录在 DB 中。
- **评论内容**：
  - 每个 loader 一行：房间地址、mrpack 下载链接（签名链接，有效期取 `ci.pack_link_ttl`，默认 168h，每次更新评论时重新签发）、对应的提交、构建与房间状态、更新时间；
  - fork PR 尚未批准时，写明如何批准；
  - PR 已关闭时，写明「已关闭」，并保留最后一次快照的 ID。
- **check run**：名称为 `vex/preview`，挂在 head sha 上。
  - 产物接受后为 `in_progress`；
  - 房间可进入（运行中或已休眠可唤醒）时为 `success`，summary 与评论内容一致；
  - 校验失败时为 `failure`，写明原因。
- **GitHub 出错的处理**：GitHub API 失败不能影响房间。按 `Retry-After` 和 rate limit 头退避，并记录在日志中。

## 7. mrpack 与客户端指纹

- **端点**：`GET …/builds/{id}/pack.mrpack`、`GET …/rooms/{id}/pack.mrpack`，权限为 V 或签名 URL。
- **包内容**：
  - `formatVersion: 1`、`game: "minecraft"`、`name`、`versionId`；
  - `dependencies`：minecraft 和 loader 的版本；
  - `origin = dep` 且带公开 URL 的文件，写进 `files`，包括 env 与 sha1/sha512；
  - `origin = build` 的 jar，放在 `overrides/mods/`；只在客户端使用的 jar，放在 `client-overrides/mods/`；
  - 服务端专用文件（包括 vex-agent）不放进包里；
  - 房间包额外包含 `overrides/servers.dat`，里面是这个房间的一条服务器记录，用 go-mc 的 NBT 写出，不压缩。
- **确定性打包**：条目按顺序排列，时间戳固定，因此相同内容两次下载得到的 sha256 一致。打包结果可以缓存。
- **客户端指纹**：Build 新增 `clientFingerprint` 字段，按设计 §9 计算，同时出现在 API 和 SSE 中。P4 会用它判断能否直接跳转。
- **兼容性实测**：在 Mac 上用 Prism Launcher 和 HMCL 实际导入、启动并进入游戏；用上游 ruri 的 `pack import` 导入。记录各启动器是否限制下载域名、`servers.dat` 是否生效。如果有启动器拒绝 `files` 中的外部 URL，就把该依赖改放进 overrides，并在报告中说明。

## 8. 连接唤醒（设计 §8）

- vexd 内置一个最小的 Minecraft 协议应答器：
  - 监听地址取 `server.wake_listen`，我们的部署为 `10.1.2.137:25566`；
  - 只处理 handshake、status 和 login start，使用已有的 go-mc 依赖。
- **房间停止时**：
  1. `router.Registrar` 把该房间的 Service 改为"无 selector + EndpointSlice"，指向应答端口；
  2. 应答器按握手中的主机名找到对应房间；
  3. status 返回休眠 MOTD；
  4. login start 时，先检查玩家名和 UUID 是否有权进入（白名单或 `preview_access`），有权限则启动房间，然后断开连接，并提示「房间正在启动，约 1 分钟后重新连接」；
  5. 无权限的玩家只收到说明，不会启动房间。
- **房间就绪后**：恢复 Pod selector。只有 Pod Ready 且路由 SLP 身份核验通过后，才能切回。
- **限速**：每个房间每分钟最多唤醒 1 次；整台服务器同时唤醒的房间数不超过可用容量。
- **安全**：应答器对 login 只做识别、不做认证（在 online-mode 下，握手阶段的身份尚未验证）。所以唤醒最多只会浪费一次启动，进入房间仍要经过服务端的 online-mode 和白名单校验。这一点写进文档。
- **NetworkPolicy**：只允许 mc-router 访问应答端口。本机防火墙同样只放行集群网段。
- 分支房间和 PR 房间一律启用唤醒；closed 状态的房间不唤醒。

## 9. GitHub 登录（device flow）

- **配置与 meta**：`auth.providers.github` 使用 App 的 client_id。配置了 GitHub 时，`/v2/meta` 的 `auth.methods` 中出现 `"github"`。
- **发起**：`POST /v2/auth/device` 由 vexd 向 GitHub 申请 device code，只返回给客户端 `{handle, userCode, verificationUri, interval, expiresAt}`。GitHub 的 device_code 只保存在服务端。
- **轮询**：`POST /v2/auth/device/poll {handle, client}`，由 vexd 代为向 GitHub 轮询，并遵守 `slow_down`。
  - 成功后，用 GitHub 返回的 token 读取 `/user`，得到身份 `github:<数字 id>`，然后立刻丢弃这个 GitHub token，不保存。
  - 按 `users.<name>.identities` 找到对应用户，签发 vex 会话。
  - 找不到对应用户时返回 `account_not_linked`。自动建号放在 P3。
- **CLI**：
  - `vex login --github`；
  - `vexd user github-id <login>`，查询 GitHub 数字 id，方便管理员写入 identities。
- **我们的部署**：把 linwhite 和 hank 的 GitHub 数字 id 写进 identities。

## P2 验收

1. **App 就绪**：App 通过 manifest 流程创建并完成安装；`vexd github check` 显示两个仓库都可以访问，权限与第 1 节一致；密钥文件权限正确，`vex-build` 读取不到。
2. **push 触发构建**：向 example 的 main 推送新提交，CI 完成后，两个轮询周期内出现 `source.kind = "ci"` 的就绪 Build，文件的三种哈希与本地重新计算的结果一致。
3. **PR 预览服**：在 example 的同仓库开一个 PR。CI 完成后数分钟内，评论中出现地址和 mrpack 链接，check 为 success。用 Prism 导入 mrpack 后直接连接，经过唤醒后成功进入；RCON 或游戏内输出确认运行的是 PR 中的版本。
4. **PR 更新**：向这个 PR 推送新提交后，评论更新，房间在无人时滚动到 generation+1，mrpack 链接也随之更新。
5. **PR 关闭**：关闭 PR 后，房间完成归档并变为 closed，评论显示「已关闭」。
6. **fork PR 审批**：从用户个人账号 fork example 并提 PR。在 `approval` 模式下，评论显示等待批准；有写权限的成员评论 `/vex preview` 后才会开房；没有写权限的人评论被忽略。
7. **恶意产物被拒绝**：分别构造路径穿越、超出大小限制、哈希不符、缺少 mod 元数据四种 artifact，均被拒绝，check 为 failure，不产生就绪的 Build。
8. **mrpack**：
   - Prism、HMCL、上游 ruri 三者都能导入；
   - 两次下载的 sha256 相同；
   - Prism 导入后，多人游戏列表中有该房间；
   - 包中不含任何服务端专用文件。
9. **连接唤醒**：
   - 停止状态的分支房间也能被唤醒；
   - 把 PR 房间设为 `preview_access = "members"`，非成员连接时只收到说明，不触发启动；
   - 限速生效；
   - 未经应答器转发的连接无法到达应答端口。
10. **GitHub 登录**：
    - `vex login --github` 能以 linwhite 身份登录；
    - 未写入 identities 的 GitHub 账号得到 `account_not_linked`；
    - 服务端日志和 DB 中都不出现 GitHub token。
11. **chorus 接入**：chorus 的 PR 合并后，main 房间使用 CI 构建启动，世界内容延续；chorus 的另一个 PR 能生成预览服。
12. **taint 测试**：第 0 节第 7 项的 taint 测试通过。
13. **报告**：写在 `docs/reports/<日期>-vex-p2.md`。需要用户操作的事项，单独列一节放在报告最前面。
