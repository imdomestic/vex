## 2. 阶段 A：chorus 来源切换到 `imdomestic/chorus`

### 2-1 访问方式

1. 先试匿名访问：`git ls-remote https://github.com/imdomestic/chorus.git`。能访问就继续用匿名 HTTPS。
2. 不能匿名访问时，改用 SSH 部署密钥：
   - 在 encore 上生成 `/var/lib/chorusd/ssh/github_chorus`（属主 chorusd，权限 0600）；
   - 用 `gh repo deploy-key add` 把公钥以**只读**方式加到 `imdomestic/chorus`；
   - remote 改为 `git@github.com:imdomestic/chorus.git`；
   - 给 chorusd 单独准备一个 GitHub 的 known_hosts，主机密钥必须和 GitHub 官方公布的指纹一致；
   - 为此在 chorusd 配置里新增 `git.ssh_identity_file` 和 `git.known_hosts_file`，gitmirror 通过 `GIT_SSH_COMMAND` 使用它们。仍然开启严格主机校验，并配真实测试。

### 2-2 切换前核对（先做，不改生产）

1. 把新仓库拉到一个临时镜像目录，列出它的分支和默认分支（`gh repo view --json defaultBranchRef`）。
2. 对比新旧仓库的提交历史。生产数据库里所有**未关闭**房间、所有构建、所有快照引用的 SHA，都要检查在新镜像里是否存在。如果迁移时改写过历史（比如为了清理敏感资源做过 filter），这些 SHA 就会对不上。
3. **遇到以下情况先停下来问用户，不要切换：**
   - 新仓库里没有 `main` 分支——直接切换的话，`main-fabric` 会被自动标记为已结束；用户可能想把它的世界带到新的默认分支房间。
   - 有未关闭房间引用的 SHA 在新仓库中不存在。

   已关闭房间和旧构建引用的 SHA 缺失，只需在报告里列出来。

### 2-3 切换

1. 修改生产配置：`git.remote`，以及按新仓库的默认分支设置 `git.default_branch`。
2. 用全新克隆在一个新目录建好镜像，**原子替换**旧镜像。旧镜像改名保留为备份，验收通过后再删除。
3. 重启 chorusd，然后确认：
   - 分支登记正确：新分支只登记、不启动；
   - Git 页显示的是新仓库；
   - 新 head 构建成功；
   - `main-fabric` 启动后用 CLI 真实进房一次；
   - 种子世界和 PVC 都保留。
4. 更新 `REPOSITORY-MIGRATION.md`（标记已完成，写明日期和核对结果）、README 和 `config/chorusd.example.toml`。

## 4. 阶段 C：Git 新鲜度、房间记录与 Ruri 列表清理

### chorusd

1. **启动前先拉取。** 启动不在运行中的分支房间之前，同步执行一次 `git fetch`，超时 10 秒。失败就用镜像里的缓存继续，并在房间 phase 里注明"使用缓存的分支信息"。
2. **清理关闭的房间记录。**
   - commit 和 asset 房间关闭超过 30 天，并且没有被保留中的快照或运行中房间的种子引用，就删除它的记录。
   - 删除时要为每个 roomId 单独保留 generation 计数（墓碑）。同一提交以后再开房时，generation 从墓碑继续。原因：快照 ID 是 `<roomId>-g<generation>`，如果计数从 1 重新开始，新快照会和旧快照撞 ID，归档就会失败。
   - 写一个真实测试：删除记录 → 同一提交再开房 → 停止并归档 → 快照 ID 不冲突。

### ruri-chorus

3. Git 页和服务器页的 Chorus 分区各加一个刷新按钮：调用 `POST /v1/git/refresh`，完成后重新加载。
4. **通用服务器列表不再显示 Chorus 的地址。** 以下两类条目一律过滤：
   - 主机名在当前 zone（取自 `/v1/meta`）或曾经用过的 zone（本地记录，包括 `100-64-0-43.sslip.io`）之下；
   - 只关联 Chorus 托管实例。

   游玩历史数据保留，只是不在列表里显示。
5. **清理 Chorus 实例的 servers.dat。** 每次启动 Chorus 托管实例前，删掉它 `servers.dat` 里主机名在 Chorus zone 下的隐藏条目。这些是 Minecraft 的 QuickPlay 自动写进去的，默认名字都叫"Minecraft Server"。只处理 Chorus 托管实例，不碰其他实例。
6. **Chorus 分区新增"最近关闭"折叠组。** 最多显示 10 个、最近 7 天内关闭的临时房间，点击可以重新开启（新的一轮 generation）。
7. **推送规则。** 第二轮的分支在用户 GUI 验收通过后推送。本轮的新提交在推送前，对**新增部分**做同样方法的扫描。

**验收**（全部用真实后端和真实实例）：

- 截图里那 5 条"Minecraft Server"从通用列表中消失；
- Chorus 实例的 `servers.dat` 里不再有 Chorus 的隐藏条目；
- "最近关闭"能列出 `ccb7f59da-fabric` 等房间，并能重新开启；
- 在 GitHub 推一个新提交后，点刷新按钮，Git 页 10 秒内就能看到；不点刷新时，最多 60 秒内也能看到。

## 5. 阶段 D：小修与磁盘

1. **示例配置。** `config/chorusd.example.toml` 同步成生产配置的实际取值：zone、`router_address`、归档开启和 chorus-archive 目标、新的 git remote。不写入任何凭据。
2. **资产 revision 的 `tankVerifiedAt`。** 一个 revision 的世界文件、元数据（以及它引用的资源包）全部在 tank 校验通过后，填上 `tankVerifiedAt`，与快照保持一致。补一个真实测试，并把现有的 plaza 1、2、3 回填。
3. **encore 磁盘。**
   - **先出一份占用明细**：
     - Nix store，其中旧 Minecraft 的 GC roots 单独列出大小；
     - `/srv/chorus` 的各个子目录；
     - k3s 的镜像和 PVC；
     - Gradle 缓存；
     - 系统 generation 的数量。
   - **只清理本项目自己产生的可回收内容**：
     - chorus 应用 profile 的旧 generation，保留最近 3 个；
     - containerd 中没有被使用的镜像；
     - 已淘汰构建残留的目录；
     - 过期的 Gradle 缓存；
     - 然后执行一次普通的 `nix-collect-garbage`，不加 `-d`，这样仍被 roots 引用的内容不会被删。
   - **不要动**：旧 Minecraft 的数据和 GC roots、用户自己的系统 generation、其他用户的文件。把它们各占多少空间写进报告，由用户决定。
   - **加一个预警**：在 `/v1/nodes` 返回 encore 根分区的可用空间；可用空间低于 20 GiB 时，Ruri Chorus 的 Chorus 分区显示提示。
