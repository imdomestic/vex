## 2. 阶段 A：修 Ruri Chorus 的钥匙串反复授权（用户在场）

**现象**：Ruri Chorus 做任何操作都会弹钥匙串授权，用户要反复输入本机密码。

**原因**：应用是 ad hoc 签名，钥匙串条目只认写入它的那个二进制的内容哈希。这带来三个问题：

- GUI 和 `ruri-cli` 被当成两个不同的程序；
- 每次重新构建，哈希都会变；
- `ChorusSettings.client()` 每次创建客户端都读一次钥匙串，所以授权弹窗会被反复触发。

**要做的事**：

1. 用 `security find-identity -v -p codesigning` 找到用户的 **Apple Development** 身份（用户已在 Xcode 里创建）。找不到就停下来告诉用户，不要改用自签证书或继续 ad hoc。
2. fork 的 `scripts/release/signing.py` 钉住的是上游作者的证书指纹。改成用户的证书，让本地构建自动用这个身份签名；`verify` 里的 team 校验也随之改成用户的 team。
3. 第一次签名时，系统会弹出"codesign 想使用钥匙串中的密钥"。用户在场，会点"始终允许"。如果签名卡住超过两分钟，提醒用户去看弹窗。
4. 重新打包后，用 `codesign -d -r-` 检查主程序和 `Contents/Helpers/ruri-cli`：两者的 designated requirement 必须一致，即 `identifier dev.ruri.launcher.chorus` 加用户的证书。
5. 确认只有主程序和 ruri-cli 访问钥匙串。ruri-monitor 和 RuriGame 如果访问了，改为由主程序把需要的数据传给它们。
6. Chorus token 改为**进程内缓存**：只在进程启动和用户修改设置时读一次钥匙串；之后的 API 调用、SSE 重连都不再读。
7. 测试不得再用临时测试程序往钥匙串写东西。只能通过签好名的 ruri-cli 写入（`chorus configure --token-stdin`）。
8. 用户第一次打开新签名的版本时，每个旧条目还会弹最后一次，让用户点"始终允许"。只有这样不起作用时，才删除 `dev.ruri.launcher.chorus.*` 条目，由用户重新登录、再写入 token。
9. 以后只保留一份应用：`/Users/linwhite/ruri-chorus/build/Ruri Chorus.app`。下载目录里那份旧副本告诉用户删掉。

**验收**：

- 用户点完"始终允许"后，你**再重新构建一次**。之后 `ruri-cli chorus rooms` 应在 10 秒内返回，不出现弹窗；用户打开 GUI，刷新服务器页、启动房间都不再弹窗。
- 用户做真实进房：在服务器页进入 `main-fabric`；在 Git 页挑一个旧提交，开临时房间进入。

两项都通过后：

- 按 P3→P4 的顺序把功能分支合进 ruri 的 `dev`；
- 执行 §9 推送到 GitHub；
- 更新 `CHORUS.md`，写清签名方式和换证书后要做的事。

## 3. 阶段 B：chorusd 修复

在 `feat/round2-fixes` 分支上完成，每条修复都要有真实组件测试（规则照上一轮 §4）。全部通过后部署，并回归 P1/P2 的核心验收：

- 启动 `main-fabric` 并真实进房（用已修好的 Ruri Chorus CLI）；
- 空闲十分钟缩容到 0；
- 再次启动后，之前放的方块仍在。

### 必须修

1. **一个房间出错不能卡住其他房间。**
   - 现状：`Reconcile` 遍历房间时，任何一个房间返回错误就整轮退出。
   - 改成：每个房间独立处理，错误记到这个房间上（phase 或 lastError），然后继续处理下一个。
   - 验收：人为制造一个调和必然失败的房间，其他房间照常推进。
2. **`lost` 必须能自动恢复。**
   - 节点持续不可用时，房间保持 lost，行为不变。
   - 节点恢复 Ready 后重新观察：
     - Pod 还在、Ready、身份匹配 → 回到 `starting`，走正常的核验流程回到 ready；
     - 其他情况 → 进入 `stopping`，复用正常停止流程（能保存就保存、缩容、归档，branch 房间保留 PVC）。
   - 验收放在阶段 D，用 seraph 做。
3. **`failed` 不能留下运行中的 Pod。**
   - 进入 failed 前先抓取日志，再把 StatefulSet 缩容到 0，保留 PVC。failed 房间不占容量名额。
   - 已经 ready 的房间如果 **Pod 仍然 Ready、只是 SLP 失败**，说明是路由问题，不要转成 failed：保持在 `starting`，phase 设为 `route unavailable`，持续重试。
   - 只有 **Pod 不 Ready** 持续超过启动期限（例如崩溃循环）时才转成 failed。
   - 验收：用真实的崩溃场景触发一次 failed，确认 Pod 已经退出、容量已经释放。
4. **健康检查不走 tailnet。** 把 `router_address` 改成 `10.1.2.137:25565`，确认 SLP 经 LAN 地址能打到 mc-router。
5. **chorusd 的可用性不能依赖 GitHub。**
   - 启动时 fetch 失败只记警告，用已有镜像继续启动。镜像为空也要启动：API 可用，构建失败时给出明确错误。
   - 构建器、事件总线、归档这些后台循环出错时，记日志并退避重试（上限 60 秒），不再让进程退出。
   - 只有配置、监听这类启动期的致命错误才退出。
   - 验收：用一个 remote 不可达的测试实例真实验证。

### 顺手修

6. 所有 Go 文件跑一次 `gofmt -w`，**单独一个提交、不改任何逻辑**；测试脚本里加格式检查。
7. mc-router 的 webhook 不再每个事件都起一次完整调和，改成合并信号：用缓冲为 1 的通道表示"尽快调和一次"。可以让 webhook 对事件中的那个房间跳过 15 秒的探测间隔。
8. `EnsureRoom` 先比较，有差异才更新：Secret、Service、StatefulSet 都不再每 5 秒无条件写一次。
9. tank 同步队列：单个任务失败不能挡住后面的任务。每个任务独立退避，从 1 分钟起逐步加到最多 1 小时。**这一条必须在 §7 启用 tank 同步之前部署。**
10. 失败的构建记录保留 7 天，之后连同日志一起清理。
11. **plaza 重新发布干净版本。** 现在的 revision 2 是测试产生的编辑快照。用 `d2map chorus publish` 重新发布原始样板世界 `/home/linwhite/d2-assets/data/handmade/v3-plaza/sample/world`，得到 revision 3，其 sha256 应与 revision 1 相同。notes 里写明是干净的重新发布。

## 4. 阶段 C：encore 的系统配置迁入 nix-config

**为什么要做**：encore 现在运行的系统，是 chorus-testbed 的 `nix/bootstrap` 在 nix-config `cc004e5` 之上叠加出来的。如果有人直接从 nix-config 重建 encore，会发生两件事：

- k3s、chorusd、DNS 全部消失；
- 六个旧 Minecraft 服务被重新启用，抢占 25565 端口。

所以 nix-config 必须成为唯一的配置来源。

**分层方案（定案）**：

- **系统层放进 nix-config**：k3s server（包括 metrics-server 的定制）、DNS、防火墙、旧服务停用与 GC 保留、chorusd 系统用户、目录规则、polkit 规则、构建模板单元、chorusd 服务单元、构建用的 JDK。
- **应用层留在 chorus-testbed**：chorusd、chorusctl 和 world-scanner 的二进制。chorus-testbed 的部署脚本负责构建它们，把结果设置到 Nix profile `/nix/var/nix/profiles/chorus`，然后 `systemctl restart chorusd`。服务单元的 ExecStart 固定指向 `/nix/var/nix/profiles/chorus/bin/chorusd`。
- 这样 nix-config 不依赖任何私有输入，hank 也能正常求值；chorusd 升级也不再需要整机切换。
- DNS 服务的单元名改成 `chorus-dns`，不再占用 `dnsmasq.service`。

**步骤**：

1. 先看 nix-config 从 `cc004e5` 以来的新提交（hank 可能推过），把 `running-system.nix` 里的差异（`services.sunshine.capSysAdmin`）落实成正式配置。
2. 在 nix-config 中构建 encore 系统，与当前运行系统做 `nix-diff` 和闭包对比。差异只允许是以下几类，逐条写进报告：
   - ExecStart 的路径；
   - DNS 单元改名；
   - nix-config 自身的新提交带来的变化。
3. 按 §6.4 的协议部署。验证 k3s、房间、chorusd、DNS、mysql、postgresql 正常，旧服务仍然 masked。
4. 从**刚推送的远端**全新克隆 nix-config，执行 `nixos-rebuild build --flake .#encore`，证明它能独立复现。
5. 停用 `nix/bootstrap`：在 README 中说明它已被 nix-config 取代，部署文档改成新的两层流程。

chorusd 的 secrets 本轮继续用文件，迁到 sops-nix 不是本轮任务。

## 5. 阶段 D：seraph 加入集群（nix-config）

1. 在 nix-config 里给 seraph 配置 k3s agent：
   - 版本 `1.35.7+k3s1`，与 encore 一致；
   - server 地址 `https://10.1.2.137:6443`，flannel 网卡 `enp11s0`；
   - 防火墙规则参照 encore（LAN 放行 10250/tcp、8472/udp，Pod CIDR 入站）；
   - join token 按 nix-config 现有的 sops-nix 方式放进 `secrets/hosts/seraph.yaml`。
2. seraph 不是全天在线，所以要开启 kubelet 的 **graceful node shutdown**，例如 `shutdown-grace-period=150s`、关键 Pod 10 秒。这样 seraph 正常关机时，房间 Pod 会收到 SIGTERM，itzg 镜像会保存世界。seraph 重新上线后，房间由 B-2 的恢复逻辑接管。本轮不实现 drain API。
3. seraph 当前不在线就跳过本阶段，在报告里标为 `待 seraph`。
4. **验收**（也就是 P2 剩下的两项，同时验证 B-2）：
   - seraph 在线时，新建的 commit 房间落在 seraph；
   - 停掉 seraph 的 k3s 服务，60 秒后房间变成 lost；
   - 重新启动 k3s，房间按 B-2 的规则恢复；
   - 确认 kubelet 配置里 graceful shutdown 已生效。真实关机测试留给用户下次关机时观察，写进报告。
