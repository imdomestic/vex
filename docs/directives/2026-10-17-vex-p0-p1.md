# 执行指令：vex P0 与 P1

- 日期：2026-10-17
- 设计依据：`docs/design/vex.md`（随本指令一起提交）
- 现状依据：`STATE-REPORT.md`（对应提交 `f035614`）

用户已确认的决定：

1. vex 是一个通用平台，使用 vex 的开发者可以接入任意第三方仓库。
2. 配置同时支持三种来源：命令行、环境变量、配置文件，优先级按此顺序从高到低。我们自己的部署由 Nix 生成 TOML。
3. 平台名称为 vex。
4. P0 中列出的清理项全部执行。

## 工作规则

- **分支**：从 `dev` 拉出 `feat/vex-p0` 和 `feat/vex-p1`，验收通过后合回 `dev`。第一个提交加入本指令和 `docs/design/vex.md`。
- **提交门槛**：每个提交都要通过 `go vet ./...`、`go test ./...` 和 Nix 构建。涉及 vex-agent 的提交还要通过 Gradle 测试。
- **不保留向后兼容**：v1 API、chorusctl 和旧配置格式直接删除。数据要迁移，接口不做兼容。
- **不可逆操作**：包括删除文件、删除 namespace 或 PVC、Nix GC、GitHub 改名、修改 tank 上的目录。执行前，先把核对结果和即将执行的命令写进报告。核对不通过就停下来报告，不要绕过。
- **tank 权限**：linwhite 在 tank 上不能执行 `sudo -n`。需要 root 时，停下来请用户执行或授权。
- **系统变更**：继续走现有的安全激活流程：构建 → dry-activate 并审阅 → 带 600 秒回滚定时器的 test → 用新 SSH 连接检查 → 持久 switch。
- **报告内容**：不得包含 token、私钥或 kubeconfig 内容。
- **阶段报告**：每个阶段结束后写一份报告，文件名为 `docs/reports/<日期>-vex-p0.md` 或 `docs/reports/<日期>-vex-p1.md`。内容包括：做了什么、验收证据（命令及结果）、偏离指令的地方及理由、遗留问题。
- **遇到设计未覆盖的情况**：选最保守的做法，并在报告中列出，不要自行扩大范围。

## P1：重命名、配置系统、项目维度

### 1A 重命名

- **全面改名**：按设计 §2 修改 Go module 路径、二进制名、包名、环境变量前缀、标签前缀、namespace、zone、数据目录、DB 文件名、systemd 单元和 polkit 规则。
- **hop-mod 改为 `agent/`**：
  - 模组名 vex-agent，mod ID 为 `vex_agent`，包名 `com.imdomestic.vex.agent`，环境变量改为 `VEX_*`。
  - 命令和逻辑保持不变，到 P4 再改。
  - 它的 jar 改为平台注入文件，通过 Build 文件路由分发。删除专用的 hop 下载路由。
- **用 `vex` 取代 chorusctl**：
  - 覆盖 chorusctl 的全部现有功能。
  - 新增 `-p/--project` 参数，默认项目可以写在用户配置里。
- **残留检查**：执行 `rg -i chorus`，在代码、Nix 和部署文件中不得有命中。允许命中的位置只有：
  - 迁移工具；
  - `docs/reports`、`docs/directives`；
  - `STATE-REPORT.md`；
  - chorus 项目自己的配置。

### 1B 配置系统（设计 §4）

- **实现内容**：
  - 四层来源：默认值、配置文件、环境变量、命令行；
  - 以 ID 为键的集合；
  - ID 格式校验，以及环境变量中 `_` 到 `-` 的解码；
  - 任一层出现未知键都报错；
  - 秘密只接受 `*_file`，命令行直接给秘密值时拒绝；
  - `vexd config show --sources` 和 `vexd config check`。
- **测试要求**，至少覆盖：
  - 标量、列表、集合条目、多层嵌套这四类配置项，每类都要测四层来源的优先级；
  - 每一层出现未知键都报错；
  - 秘密从命令行传入时被拒绝；
  - ID 解码；
  - `config show --sources` 的 golden 测试。
- **vex CLI** 使用同一套实现，配置文件为 `~/.config/vex/config.toml`，例如 `VEX_URL`、`VEX_TOKEN_FILE`、`--url`。
- **Nix 模块**：
  - 移到 vex 仓库的 flake，作为 `nixosModules.vexd`，`settings` 通过 `pkgs.formats.toml` 生成。
  - nix-config 中 encore 的 chorus 模块改为 import 这个模块并写 settings。
  - seraph 只同步名称。
  - tank 上的用户 `chorus-archive` 改为 `vex-archive`，归档根改为 `/srv/archive/vex`，原 `legacy/` 迁到 `/srv/archive/vex/legacy/`。
- **白名单**：删除 `hank_whitelist`，改为由项目成员的 MC 账号自动生成，再加上 `projects.<p>.whitelist`。

### 1C 项目维度与权限

- **Git**：
  - 每个项目一个镜像，路径为 `<data>/projects/<p>/git.git`。
  - 凭据只对本项目生效。所有 git 调用都要清除继承来的配置：执行 `-c credential.helper=`、unset `GIT_ASKPASS`、`SSH_AUTH_SOCK`。
  - 凭据按类型注入：
    - SSH 私钥：通过 `GIT_SSH_COMMAND`，带 `IdentitiesOnly=yes` 和项目自己的 `known_hosts`；
    - HTTPS token：通过单次调用的 credential helper 注入。
- **存储与路径**：
  - DB 记录带上项目前缀，counter 也按项目区分（设计 §5）。
  - Runtime 中记录 namespace 和 k8s 对象名。
  - 快照、世界、资源包、传输记录中保存相对路径。
- **Kubernetes**：
  - vexd 为每个项目创建 namespace `vex-p-<p>`，带 ResourceQuota、LimitRange 和 NetworkPolicy。本轮的 NetworkPolicy 只要求：房间入站仅限 mc-router；出站拒绝 LAN 和 100.64.0.0/10，但放行 vexd 的 API 端口。
  - RBAC 改为 ClusterRole，代码中强制检查 namespace 前缀。
- **路由与 DNS**：
  - 房间地址改为 `<room>.<project>.vex.internal`。
  - 同步修改 dnsmasq 配置和 h610 上 Headscale 的 split DNS。
  - 实测 mc-router 能否跨 namespace 发现 Service。不能的话，改为由 vexd 通过 mc-router 的路由 API 下发映射。在报告中写明采用了哪种方式。
- **调度**：
  - 用 `nodes.*`（roles、priority、max_rooms）替换写死的 seraph→encore 顺序。
  - 节点磁盘指标改从 kubelet stats summary 获取。
- **构建（本轮仍在宿主机上执行）**：
  - 只有 `trust = "trusted"` 的项目可以构建，其他项目返回 409 `sandbox_unavailable`。
  - worker 改用独立的系统用户 `vex-build`，读不到以下内容：`/var/lib/vex/secrets`、`/var/lib/vex/ssh`、kubeconfig、DB。
  - 源码 checkout 和产物收集由 vexd 完成。
  - Gradle 缓存按项目隔离，路径为 `<data>/projects/<p>/cache/gradle`。
- **loader 配置**：移到 `projects.<p>.loaders.*` 下，字段与现在相同。到 P2 再迁入 vex.toml。
- **去掉 chorus 专属语义**：
  - `requires.chorusMod` 改为 `requires.mods`；
  - `chorus-checkpoint.json` 改为项目配置 `projects.<p>.worlds.extra_root_entries`；
  - 从 vex CLI 和 world-scanner 中删除 d2-assets 敏感路径检查，并在报告中注明这个检查应由 d2map 承担。
- **认证与权限**：
  - 用户凭据改为 `token_sha256`。
  - 角色和各接口的权限按设计 §5 和 §12 实现。请求无权访问的项目一律返回 404。
  - 房间 token 的声明中加入 project。下载时要检查文件确实属于该房间的 Build 或 seed。
- **API**：
  - 实现设计 §12 中除 B 类接口（P2）和 delegate（P4）以外的全部端点，并删除 v1。
  - 把 `docs/api.md` 改写为 v2 文档，同时加一个测试：路由表与文档中的端点必须一一对应。
- **SSE**：
  - 每个事件都带 `project`，支持 `?project=` 过滤。
  - 新增 `room_deleted`、`build_deleted`、`snapshot`、`world`、`pack` 事件。
  - 修复报告 §11.1 中的两个问题：
    - `sync` 读取 Room 和 Build 时要放在同一个读事务里；
    - 单房间订阅遇到记录已删除时，不能中断轮询。

### 1D 数据迁移

- **迁移工具**：命令为 `vexd migrate chorus --from-db /srv/chorus/state/chorusd.db --from-dir /srv/chorus --project chorus`。先用 `--dry-run` 输出完整的迁移计划，写进报告后再正式执行。
- **用户 token**：读取现有的 users.toml，计算 sha256，输出可以直接放进 settings 的 TOML 片段。这样 ruri 钥匙串里的 token 和 hank 的 token 都能继续使用。输出中不得包含 token 原文。
- **本地文件**：在同一文件系统上 rename 到新布局：
  - snapshots → `projects/chorus/snapshots`；
  - assets → `projects/chorus/worlds`；
  - packs → `projects/chorus/packs`；
  - gradle-home → `projects/chorus/cache/gradle`。
  构建产物不迁移，需要时重新构建；git 镜像重新 clone。
- **tank**：把 `/srv/archive/chorus/{snapshots,assets,packs}` 移到 `/srv/archive/vex/projects/chorus/{snapshots,worlds,packs}`。这一步需要 root。移动后抽样比对 sha256，并确认所有传输记录仍为 verified 状态。
- **房间记录**：
  - closed 状态的房间作为 closed 记录迁移，保留快照的来源信息；墓碑一并迁移。
  - 租约和 runtime 数据丢弃。
  - main 房间新建为 `chorus/main-fabric`，seed 使用 P0 第 2 步记录的快照。
- **清理旧资源**：等 P1 验收第 3、7 项都通过后，先列出待删除的清单，再删除 namespace `chorus-rooms`（连同旧的 main PVC）和 `/srv/chorus`。
