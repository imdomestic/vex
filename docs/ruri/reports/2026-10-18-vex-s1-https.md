## 内部 HTTP 来源限制

【实测】encore、seraph 的 PodCIDR 分别为 `10.42.0.0/24`、`10.42.1.0/24`。原有宿主防火墙对 wlo1 开放 TCP 8790，并允许 cni0、flannel.1 上的集群来源。

【代码】已有 runtime 项目 NetworkPolicy 为所有项目 Pod 放行实际 `internal_base_url` 对应的 `10.1.2.137/32`、TCP 8790，同时拒绝普通内网出站。该策略控制项目 Pod 的出站行为。

【实测】seraph 的实际 `FLANNEL-POSTRTG` 对 PodCIDR 发往普通 LAN 的流量执行 MASQUERADE。临时 namespace `vex-p-vex-it-s1-source` 中的真实 BusyBox Pod 位于 seraph，PodIP=`10.42.1.26`；它连接现有 `10.1.2.137:8790` 后，encore 的 `ss -ntp` 显示 API 对端为 `10.1.2.194`。两节点 nftables 的反向路径检查也要求来源与入站接口一致。

【代码】seraph 的独立 nft nat 表仅匹配 cni0→enp11s0、`10.42.1.0/24→10.1.2.137`、TCP 8790，在 `srcnat-1` 优先级使用 `snat to ip saddr` 保持 Pod 地址，供应用验证身份。encore 对同一目的地址与端口允许 wlo1 上的 `10.42.1.0/24`，并增加同范围反向路径检查例外；seraph 对经 flannel 返回的已建立连接增加对应例外。实际 seraph 上 `nft --check` 已通过。

【代码】encore 独立 nftables input chain 的优先级为 -10，仅匹配目标 `10.1.2.137:8790`：允许 loopback；允许 cni0/flannel.1 上两个实际 PodCIDR；允许上述 seraph Pod 来源；其他来源丢弃。尾网 TLS 8790、SSH和其他服务规则保持现有配置。

【边界】PodCIDR 规则本身没有 namespace 身份信息。应用内部监听器通过真实 Kubernetes PodIP、项目 namespace、标签、ServiceAccount 和真实 owner UID 验证房间 Pod、归档 Job 与 mc-router，原有 HTTP 鉴权继续执行。容器开始请求时 kubelet 可能尚未发布 PodIP；检查使用共同 10 秒 context 并发等待真实状态事件，确认身份后才允许请求继续。部署健康检查通过尾网 HTTPS 执行。

【实测】来源检查 namespace UID=`72c76593-a1da-4935-8186-8a334da66237`，Pod UID=`56cd8740-581c-4729-b29c-6e9bd82b8b26`。检查后使用 Kubernetes DeleteOptions UID precondition 删除 namespace；再次 GET 返回 NotFound，没有创建 PVC 或运行 Minecraft。
