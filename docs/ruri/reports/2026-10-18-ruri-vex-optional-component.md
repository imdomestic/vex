# Ruri Vex 按需安装组件评估

日期：2026-10-18。调查对象为 `/Users/linwhite/ruri-vex-experimental` 的 P1 提交 `61dc1df` 与当前未提交的 R2 工作目录。本次只读取代码、构建产物和官方文档，写入调查报告；组件拆分和新增 Swift 依赖均未实施。

## 用户要求对应的边界

Vex 可以作为启用实验性选项后下载的完整组件：默认应用与默认构建依赖图不包含 Vex 业务代码、页面、命令、EventSource 和拟新增的 HTTP 库；用户启用时下载与当前 Ruri 版本及 CPU 架构匹配的预编译组件。

主程序仍需保留实验选项、组件安装与验证、启停管理，以及供组件调用的启动器接口。原有的 Vex 专属接入可以改为固定的可选功能接口；账号登录、实例管理、MRPack 导入和游戏启动继续由 Ruri 本体执行。这些入口在未安装或关闭组件时保持空闲。

以上属于可行性判断。当前仓库尚无可下载代码组件的安装器、加载协议或发布产物。

## 可选择的完整实现

| 事项 | A：完整原生扩展包（推荐） | B：独立伴随应用 |
| --- | --- | --- |
| 安装时机 | 用户启用时下载完整组件 | 用户启用时下载完整组件 |
| 默认包 | 保留组件管理与宿主接口 | 保留组件管理与宿主接口 |
| Vex 页面 | 加载组件后仍在 Ruri 的服务器页、Git 页和设置中显示 | Vex 项目、服务器、Git 和设置显示在独立窗口 |
| Vex 业务与依赖 | 全部进入下载的代码 bundle 及其资源 | 全部进入下载的伴随应用及其资源 |
| CLI | `ruri vex` 通过已加载组件提供命令、帮助、schema 和执行 | `ruri vex` 委托已安装的伴随组件执行 |
| Ruri 能力复用 | 通过宿主接口调用账号状态、实例更新和启动 | 通过版本化 IPC 调用同一组能力 |
| HTTP 支持 | AsyncHTTPClient 只进入可选组件；主程序 ATS 保持原配置 | 伴随应用可以拥有自己的 HTTP 配置，继续使用 URLSession 和 EventSource；具体配置需实际打包验证 |
| 关闭功能 | 取消任务、移除页面与命令；当前进程已加载的代码可能继续留在内存，应用退出后释放 | 取消任务并结束伴随进程 |
| 版本关系 | 组件匹配宿主发布版本、接口版本、架构及签名要求 | 组件与宿主核对 IPC 版本、架构及签名要求 |

建议选择 A，保留现有的 Ruri 窗口和页面操作方式。该选择同时包含将 EventSource、Vex 代码和资源移出默认构建，以及把 AsyncHTTPClient 限定为可选组件依赖。B 适合希望 Vex 拥有独立窗口和独立进程的使用方式。

两项均需要重构当前直接访问 AppModel 和 Core 内部成员的调用。宿主接口不提供 Microsoft 凭据，实例文件操作由宿主校验。A 的原生组件作为可信发布代码运行，与宿主共享进程权限；接口约束无法提供系统隔离。B 使用独立进程，宿主通过 IPC 提供限定的能力。

## A 的完整组件划分

### 默认 Ruri 本体

- 组件启用状态、下载进度、错误提示、更新状态和卸载入口。
- 组件清单验证、下载、完整性检查、签名检查与加载器。
- 通用页面容器、服务器分区入口、设置容器、CLI 命令发现与执行入口、URL 入口分发。
- 受限宿主能力：查询可用账号和实例、准备及更新 MRPack、检查托管文件、发起或取消启动、查询游戏会话与进度。
- 用户启用状态读取；未启用时不解析组件设置、不读取 Vex 钥匙串、不加载组件、不检查组件更新。

主程序保留这些能力的接口和原有实现。Vex 服务器、项目、房间、PR、邀请和设备登录模型属于下载组件。

### 下载组件

- Vex API、SSE、登录流程、会话状态、房间加入判定和取消逻辑。
- 服务器、Git、PR、设置等全部 Vex 视图，组件自己的可观察状态与本地化资源。
- `ruri vex` 的命令定义、帮助、schema、文本输出与执行。
- Vex 托管实例映射、文件集合与指纹判定、交给宿主执行的 MRPack 更新要求。
- EventSource 和 AsyncHTTPClient，以及组件实际使用的传递依赖与许可证。
- 组件入口、版本清单和资源文件；测试数据只属于测试产物。

### 宿主与组件接口

当前 `AppModel` 是主程序的内部类型，`RuriCore` 也没有为外部二进制建立兼容接口。组件应通过明确的接口交换数据、调用宿主能力；UI 可以由组件返回 `NSViewController`，由宿主的 SwiftUI 容器展示。CLI 使用参数、命令描述、结果和退出码接口，避免跨边界传递具体的 Vex 命令类型。

MRPack 导入、更新、文件事务、实例锁和实际启动继续由宿主执行。组件提供本地包、目标实例、文件校验条件及操作身份，接收进度、完成结果或错误。接口保留 generation/build 校验、一次加入最多启动一次、任务取消，以及托管文件冲突立即失败等现有语义。

### 签名与二进制兼容

当前 RuriCore 没有独立动态库，也没有开启可供外部组件依赖的稳定二进制接口；Swift 语言的 ABI 稳定不等于现有 AppModel/Core 内部接口已经稳定。组件发布时需要绑定明确的宿主接口版本；兼容范围应完整规定为同一 Ruri 发布版本、对应架构与已验证工具链组合。跨边界使用受约束的 Foundation/AppKit 接口，不直接交换内部 Swift 类型。

组件安装器需要验证可信发布者和产物签名。当前本机构建目录是 ad hoc 产物，尚无组件签名发布渠道；正式自动分发还需建立组件的签名、发布清单和系统接受条件。采用 Hardened Runtime 的宿主加载动态代码时，还需符合 Apple 的 library validation 规则。最终向上游提交时，发布者与签名关系必须由上游明确接受；本次不会联系上游。

B 的 HTTP 请求集中在伴随 `.app` 进程内，其 CLI 通过 IPC 委托网络操作。独立 CLI 可执行文件是否具备对应的主 bundle 信息需要单独验证，不能直接继承伴随应用的 ATS 配置作为实现前提。

## 安装、更新与关闭行为

1. **首次启用**：读取可信发布位置的组件清单，选择当前宿主版本与架构对应的完整产物；展示下载进度。下载完成后检查大小、摘要、发布签名、代码签名及接口版本，全部通过才安装并启用。失败时显示具体原因，保持禁用。
2. **组件位置**：使用 Ruri 支持目录下单独的版本化组件目录，不修改已签名的 `Ruri.app` 包内内容。默认安装和未启用状态不创建 Vex 服务器会话。
3. **网络与凭据**：组件下载使用宿主原有 HTTPS 能力。Vex HTTP 请求使用用户配置的服务器地址；HTTPS 继续验证证书和主机名。Keychain 读写继续由主程序与 ruri-cli 执行；组件经宿主接口取得所属服务器的 Vex 会话。Microsoft 登录和启动凭据由宿主处理，接口不向组件返回这些凭据。A 仍具有前述共享进程权限的限制。
4. **关闭功能**：取消 SSE、轮询、下载和未完成加入操作，撤销页面、CLI 命令和启动前扩展回调。已启动的 Minecraft 进程按普通游戏会话继续管理。已下载文件和用户配置可以保留供重新启用使用。
5. **删除组件**：提供明确的卸载操作。A 已加载代码的删除与卸载须考虑当前进程仍持有代码和对象；应用重新启动时确认不再加载。用户的游戏世界与实例数据独立于组件文件。
6. **Ruri 更新**：新版本先检查已安装组件的兼容性。启用状态下取得兼容组件后再运行；组件不兼容或下载失败时明确提示，普通 Ruri 功能继续可用。未启用状态下不下载 Vex 更新。
7. **CLI 与链接**：未安装或未启用时，上游 CLI 的 help、发现和 schema 保持原有输出。打开 Vex 链接时展示启用入口，由用户主动开启组件后继续处理。

现有服务器设置、实例映射、托管标记和 Vex 会话必须保留。宿主可保存不透明的组件配置，组件负责解释其内容；未安装组件时，普通设置写入也必须保留这些字段。卸载组件只处理组件文件，世界、实例和账号数据继续独立保存。GUI 与 CLI 共用安装状态，并通过安装锁避免同时安装不同组件版本。

## 对既有上游改动的处理

| 目前的改动 | 按需安装后的归属 |
| --- | --- |
| Package 中的 EventSource、Vex 源码与资源 | 单独组件的构建清单；默认 Package 不解析这些依赖 |
| Page/RootView 对 Vex 类型的直接引用 | 宿主的固定可选功能接口与页面容器；具体页面在组件 |
| ServersView 的 Vex 分区与过滤规则 | 宿主提供分区及过滤入口，组件提供具体规则 |
| PreferencesView 的 Vex 设置 | 宿主展示安装/启停状态，组件提供完整服务器设置 |
| AppSettings 内的 Vex 配置类型 | 宿主保留启用信息，Vex 配置由组件管理 |
| CLI 注册、帮助、schema、输出中的 Vex 类型 | 宿主保留扩展发现入口，具体实现随组件安装 |
| 启动前服务器列表整理 | 宿主保留受约束的启动前回调，组件提供 Vex 规则 |
| Vex 本地化、许可证和测试数据 | 组件资源与组件测试；默认应用仅保留组件管理文字 |
| 签名、应用标识、原版钥匙串和 Sparkle | 沿用宿主原有规则，新增组件自身的构建、验证与发布步骤 |
| SDL 正常退出等通用修复 | 保持独立的普通启动器修改，按其自身条件审阅和测试 |

组件需要独立构建清单。仅在同一 Package 中增加 target 或设置运行时开关，仍可能让默认构建解析组件依赖；分开的构建清单可明确默认产品的依赖范围。

## 验收条件

- 新安装的默认应用不包含 Vex 实现、EventSource、AsyncHTTPClient、Vex 翻译和 Vex 测试资源；允许保留组件入口文字。检查依赖解析结果、包内文件、动态依赖与符号。
- 未安装和已安装但关闭两种状态，GUI、CLI golden、钥匙串访问和网络行为均满足 R1 的关闭要求。
- 首次启用、重复启用、下载取消、下载失败、签名失败、版本不匹配均有确定结果；未通过校验的代码不执行。
- 正式 HTTP 域名上的 GUI 邀请登录、多服务器分组、会话失效、单服务器断开和 SSE 恢复完成真实验收。
- MRPack 同步、非托管文件保留、冲突拒绝、指纹跳过，以及真实进房和 generation 判定继续通过。
- 关闭组件时没有残留连接和加入任务；重新开启能够恢复；宿主更新和组件卸载按上述生命周期验证。
- 宿主与组件分别运行构建、测试、本地化与密钥扫描，发布产物分别验证签名和版本对应关系。

本次没有建立组件原型，因此安装包体积、首次下载耗时、加载耗时和组件更新的实际结果均没有测量值。
